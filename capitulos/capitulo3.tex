\chapter{Desarrollo}

En este capítulo se describe el proceso de diseño, construcción e implementación de la Plataforma de Análisis Estadístico Académico para la Universidad Politécnica de Texcoco, abarcando desde el marco metodológico adoptado hasta la arquitectura técnica del sistema, el modelo de datos, el desarrollo del backend y frontend, el procesamiento de información estadística y la infraestructura de despliegue.

% ============================================================
\section{Metodología: Kanban}
\label{sec:metodologia-kanban}
% ============================================================

Para el desarrollo de la plataforma se adoptó \textbf{Kanban} como metodología ágil ligera, la cual pertenece al marco de las metodologías ágiles y se fundamenta en la gestión visual del flujo de trabajo. A diferencia de otras metodologías ágiles que estructuran el trabajo en iteraciones fijas (sprints), Kanban propone un \textbf{flujo continuo} donde las tareas avanzan de forma progresiva por un tablero visual dividido en columnas que representan los estados del proceso.

El término Kanban proviene del japonés y significa \textit{señal visual} o \textit{tarjeta}. Esta metodología fue desarrollada originalmente por Toyota en la industria manufacturera y posteriormente adaptada al desarrollo de software por David J. Anderson, quien formuló los principios y prácticas esenciales del método.

\subsection{Principios de Kanban Aplicados al Proyecto}

Los cuatro principios fundamentales de Kanban que guiaron el desarrollo de esta plataforma son:

\begin{enumerate}
    \item \textbf{Visualización del flujo de trabajo:} Todas las tareas del proyecto (funcionalidades, correcciones, mejoras de esquema de base de datos) se representaron como tarjetas en un tablero, permitiendo al equipo identificar el estado de avance de cada componente en todo momento.

    \item \textbf{Limitación del trabajo en progreso (WIP --- Work In Progress):} En cada etapa del tablero se limitó el número de tareas activas simultáneamente. Esto evitó la sobrecarga del equipo y aseguró que cada módulo fuera completado y validado antes de iniciar el siguiente.

    \item \textbf{Gestión del flujo continuo:} En lugar de planificar iteraciones de duración fija, las tarjetas de trabajo fluyeron de manera continua desde el estado \textit{Pendiente} hasta \textit{Desplegado}, priorizando aquellas funcionalidades con mayor impacto en los usuarios de la Dirección Académica.

    \item \textbf{Mejora continua (Kaizen):} Durante el desarrollo se realizaron reuniones periódicas de revisión en las que se analizaron cuellos de botella, se corrigieron decisiones de diseño previas y se refinaron tanto el esquema de datos como las interfaces de usuario.
\end{enumerate}

\section{Requerimientos del Sistema}
% ============================================================

Con base en el documento de requerimientos de software y las reuniones sostenidas con los usuarios de la Dirección Académica, se identificaron los siguientes requerimientos:

\subsection{Requerimientos Funcionales}

\begin{itemize}
    \item \textbf{RF-01:} El sistema debe permitir la carga masiva de datos académicos históricos mediante archivos CSV o Excel (.xlsx/.xls) de hasta 200 MB.
    \item \textbf{RF-02:} El sistema debe validar automáticamente cada fila de los archivos cargados, reportando los errores por columna con su valor inválido y el motivo.
    \item \textbf{RF-03:} El sistema debe calcular y mostrar los indicadores: Matrícula Actual, Aprovechamiento, Reprobación, Deserción, Eficiencia Terminal, Índice de Titulación, Cobertura y Evaluación Docente.
    \item \textbf{RF-04:} El sistema debe presentar los indicadores en tableros gráficos interactivos con filtros por subsistema educativo, ciclo escolar, cuatrimestre y programa educativo.
    \item \textbf{RF-05:} El sistema debe permitir la gestión de usuarios con tres niveles de acceso: administrador general, administrador escolar y usuario consultor.
    \item \textbf{RF-06:} El sistema debe generar reportes descargables en formato PDF.
    \item \textbf{RF-07:} El sistema debe registrar en una bitácora de auditoría todas las acciones relevantes de los usuarios.
    \item \textbf{RF-08:} El sistema debe permitir la administración del catálogo de ciclos generacionales y subsistemas.
\end{itemize}

\subsection{Requerimientos No Funcionales}

\begin{itemize}
    \item \textbf{RNF-01:} El procesamiento de archivos CSV masivos debe realizarse de forma asíncrona para no bloquear la interfaz del usuario.
    \item \textbf{RNF-02:} La autenticación debe implementarse mediante JSON Web Tokens (JWT) con tokens de acceso de 15 minutos y tokens de refresco de 7 días.
    \item \textbf{RNF-03:} Las contraseñas deben almacenarse con el algoritmo criptográfico Argon2, resistente a ataques de fuerza bruta.
    \item \textbf{RNF-04:} El sistema debe limitar las peticiones a 120 solicitudes por minuto por dirección IP para prevenir ataques de denegación de servicio.
    \item \textbf{RNF-05:} El sistema debe estar completamente contenedorizado mediante Docker para garantizar la portabilidad entre entornos.
    \item \textbf{RNF-06:} El tiempo de respuesta de la API no debe superar los 500ms en condiciones normales de operación.
\end{itemize}

\subsection{Actores del Sistema}

\begin{itemize}
    \item \textbf{Administrador General:} Acceso total al sistema. Gestiona usuarios, subsistemas, ciclos generacionales y tiene acceso a la bitácora de auditoría.
    \item \textbf{Administrador Escolar:} Puede cargar archivos de datos para su subsistema asignado y visualizar todos los indicadores.
    \item \textbf{Usuario Consultor:} Acceso de solo lectura a los tableros estadísticos y reportes del sistema.
\end{itemize}

\section{Arquitectura del Sistema}
% ============================================================

El sistema adopta una \textbf{arquitectura de tres capas} en su concepción lógica, implementada físicamente mediante contenedores Docker orquestados con Docker Compose. El flujo de tráfico se estructura de la siguiente manera:

\begin{center}
$ \texttt{Nginx (Puerto 80)} \longrightarrow \begin{cases} \texttt{React SPA} & \text{(archivos estáticos)} \\ \texttt{FastAPI} & \text{(peticiones /api/*)} \end{cases} \longrightarrow \begin{cases} \texttt{PostgreSQL 16} \\ \texttt{Redis 7} \longleftrightarrow \texttt{Celery Worker} \end{cases} $
\end{center}

\subsection{Capa de Presentación (Frontend)}

Desarrollada en React 18 con TypeScript y compilada por Vite, esta capa implementa una \textbf{Aplicación de una Sola Página (SPA)} que se carga completamente en el primer acceso del navegador. Todas las interacciones posteriores consumen únicamente datos en formato JSON desde la API, sin recargar la página completa. Los tableros estadísticos se renderizan mediante Apache ECharts, y el estado global de los filtros se administra con Zustand.

\subsection{Capa de Lógica de Negocio (Backend)}

El núcleo del sistema está implementado con FastAPI sobre Python 3.12. Esta capa expone 15 routers con endpoints REST, aplica las reglas de validación mediante Pydantic, gestiona la autenticación mediante JWT y coordina el procesamiento asíncrono de archivos a través de Celery. Las interacciones con la base de datos se realizan de forma asíncrona mediante SQLAlchemy 2.0 con el driver \texttt{asyncpg}.

\subsection{Capa de Datos y Mensajería}

\begin{itemize}
    \item \textbf{PostgreSQL 16:} Almacena de forma persistente todos los datos académicos e institucionales, con propiedades ACID garantizadas.
    \item \textbf{Redis 7:} Actúa como broker de mensajería entre FastAPI y los workers de Celery, almacenando temporalmente las tareas de procesamiento pendientes y sus resultados.
    \item \textbf{Celery Worker:} Proceso independiente que ejecuta en segundo plano el análisis, validación y carga masiva de archivos CSV y Excel, sin bloquear el hilo principal de la API.
\end{itemize}

\subsection{Autenticación y Control de Acceso}

El sistema implementa autenticación sin estado mediante JWT. Al iniciar sesión, el servidor genera dos tokens firmados con una clave secreta aleatoria de 32 bytes:

\begin{itemize}
    \item \textbf{Token de Acceso:} Vigencia de 15 minutos. Se incluye en la cabecera \texttt{Authorization: Bearer \textless token\textgreater} de cada petición a la API.
    \item \textbf{Token de Refresco:} Vigencia de 7 días. Se utiliza únicamente para solicitar un nuevo token de acceso sin requerir credenciales nuevamente.
\end{itemize}

El control de acceso basado en roles (RBAC) se implementa mediante dependencias de FastAPI (\texttt{Depends}) que verifican el campo \texttt{role} del token decodificado antes de permitir el acceso a cada endpoint protegido.

\section{Procesamiento de Datos: Pandas y Celery}
% ============================================================

El módulo de carga de archivos es el componente más complejo del sistema. Su diseño responde al requerimiento de procesar archivos de hasta 200 MB sin degradar la experiencia del usuario. El flujo de procesamiento es el siguiente:

\begin{enumerate}
    \item El usuario selecciona y sube un archivo CSV o Excel desde la interfaz web.
    \item FastAPI recibe el archivo, lo almacena temporalmente en el servidor y registra un \texttt{UploadJob} en la base de datos con estado \texttt{pending}.
    \item FastAPI encola una tarea en Celery a través del broker Redis y responde de inmediato al cliente con el identificador único del trabajo (\texttt{job\_id}).
    \item El worker de Celery retoma la tarea de la cola y ejecuta el procesamiento completo:
    \begin{itemize}
        \item Parsea el archivo con Pandas, detectando automáticamente el separador, la codificación y la fila de encabezados.
        \item Valida cada fila: tipo de dato, valores negativos, valores fuera de rango, valores no permitidos según el catálogo y consistencia con la base de datos.
        \item Elimina duplicados internos en el archivo mediante las claves de deduplicación definidas por tipo de dataset.
        \item Ejecuta un \textit{upsert} masivo en PostgreSQL mediante \texttt{INSERT ... ON CONFLICT DO UPDATE}.
    \end{itemize}
    \item El \texttt{UploadJob} se actualiza con el resultado: filas procesadas, filas con error y lista detallada de los primeros 500 errores.
    \item La interfaz del usuario consulta periódicamente el estado del job hasta que el procesamiento concluye.
\end{enumerate}

El sistema define 7 tipos de dataset con sus campos obligatorios, opcionales, valores permitidos y restricciones numéricas:
\texttt{matricula}, \texttt{evaluacion\_academica}, \texttt{titulacion}, \texttt{evaluacion\_docente}, \texttt{becas}, \texttt{discapacidad} y \texttt{etnia}.

\section{Cálculo de Indicadores Académicos}
% ============================================================

Los indicadores estadísticos calculados por el sistema corresponden a las métricas oficiales de evaluación institucional. Las fórmulas matemáticas implementadas son las siguientes:

\begin{table}[H]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Indicador} & \textbf{Fórmula} \\
\hline
Matrícula Actual & $M = T - B_r - B_d + NI$ \\
\hline
Índice de Reprobación & $IR = \dfrac{B_r}{T} \times 100$ \\
\hline
Índice de Deserción & $ID = \dfrac{B_d}{T} \times 100$ \\
\hline
Aprovechamiento & $A = \dfrac{\sum (P_{PE} \times N_{PE})}{\sum N_{PE}}$ \\
\hline
Eficiencia Terminal & $ET = \dfrac{CE}{MG} \times 100$ \\
\hline
Índice de Titulación & $IT = \dfrac{TIT}{CE} \times 100$ \\
\hline
Cobertura & $COB = \dfrac{M}{PEE}$ \\
\hline
Absorción NMS & $ABS = \dfrac{E_{NMS}}{NI}$ \\
\hline
\end{tabular}
\caption{Fórmulas matemáticas de los indicadores institucionales.}
\end{table}

Donde: $T$ = total de alumnos, $B_r$ = bajas por reprobación, $B_d$ = bajas por deserción, $NI$ = nuevo ingreso, $P_{PE}$ = promedio del programa educativo, $N_{PE}$ = número de alumnos del PE, $CE$ = concluyeron estudios, $MG$ = matrícula generacional, $TIT$ = titulados, $PEE$ = población en edad escolar, $E_{NMS}$ = egresados de nivel medio superior.

Todos los indicadores soportan filtros dinámicos por subsistema, ciclo escolar, cuatrimestre y programa educativo, calculándose en tiempo real sobre los datos almacenados en PostgreSQL.

\section{Infraestructura y Despliegue}
% ============================================================

Además de programar la aplicación, fue necesario preparar el lugar donde esta se ejecutaría de forma permanente y accesible para el personal de la Dirección Académica. Esta sección describe, de manera general, cómo se acondicionó el servidor que aloja la plataforma y de qué manera las tarjetas del tablero Kanban correspondientes a la columna \textit{Desplegado} (Sección \ref{anexo:kanban-migraciones}) llegan a convertirse en un sistema realmente disponible en internet.

\subsection{Preparación del Servidor}

El sistema se aloja en un equipo físico con sistema operativo Ubuntu Linux, dedicado a mantener en funcionamiento los servicios de la universidad las 24 horas del día. Antes de instalar la plataforma fue necesario:

\begin{itemize}
    \item Configurar el acceso remoto y administrativo al equipo mediante el protocolo SSH, de forma que el sistema pudiera instalarse, actualizarse y supervisarse sin necesidad de tener acceso físico a la máquina.
    \item Instalar Docker, la herramienta encargada de ejecutar la aplicación de manera aislada y ordenada (véase la Sección \ref{sec:docker-infra}).
    \item Configurar un cortafuegos (\textit{firewall}) que únicamente permite el paso de las conexiones estrictamente necesarias para el funcionamiento del sistema, bloqueando cualquier otro intento de acceso al servidor.
\end{itemize}

\subsection{Publicación del Sistema en Internet}

Dado que el servidor no cuenta con una dirección de internet fija (esto ocurre comúnmente en conexiones residenciales o institucionales de bajo costo, donde la dirección puede cambiar de vez en cuando), fue necesario emplear un servicio de \textbf{DNS dinámico}. Este servicio mantiene actualizado, de manera automática y cada pocos minutos, el nombre de dominio de la plataforma (\texttt{estadistica.ddns.net}) para que siempre apunte a la dirección real del servidor, sin importar si esta cambia con el tiempo. Gracias a esto, los usuarios de la Dirección Académica pueden acceder al sistema escribiendo siempre el mismo nombre en su navegador, sin necesidad de conocer ni actualizar manualmente ninguna dirección técnica.

\subsection{Cifrado de las Comunicaciones (HTTPS)}

Toda la información que viaja entre el navegador del usuario y el servidor —incluyendo las contraseñas y los datos académicos— se transmite de forma cifrada mediante el protocolo HTTPS. El certificado digital que hace posible este cifrado fue obtenido de manera gratuita a través de la autoridad certificadora \textit{Let's Encrypt}, utilizando la herramienta \texttt{certbot}, la cual además se encarga de renovar automáticamente el certificado antes de que expire, sin requerir intervención manual.

\subsection{Nginx como Puerta de Entrada del Sistema}

Todas las peticiones que llegan al servidor pasan primero por Nginx, que funciona como una especie de recepcionista: recibe cada conexión entrante, decide hacia dónde debe redirigirla y devuelve la respuesta correspondiente. En el caso de esta plataforma, Nginx cumple tres funciones principales:

\begin{itemize}
    \item Redirige automáticamente las conexiones que llegan sin cifrar (HTTP) hacia su versión seguras (HTTPS).
    \item Reenvía cada solicitud del usuario hacia el contenedor de la aplicación que corresponde, sin que el usuario perciba que, internamente, el sistema está dividido en varios componentes independientes.
    \item Publica de forma directa algunos archivos de consulta pública del proyecto, como los manuales de usuario y los diagramas del sistema.
\end{itemize}

\subsection{Empaquetado de la Aplicación con Contenedores Docker}
\label{sec:docker-infra}

Para evitar los problemas comunes de instalación (``en mi computadora sí funciona''), la aplicación completa se empaquetó mediante \textbf{Docker}, una herramienta que permite ejecutar cada componente del sistema dentro de un contenedor: un entorno aislado y autosuficiente que ya incluye todo lo necesario para funcionar (lenguaje de programación, librerías y configuración), sin depender de lo que esté instalado en el servidor. Esto garantiza que el sistema se comporte exactamente igual en el equipo de desarrollo que en el servidor de producción.

Mediante Docker Compose se orquestan 5 contenedores que trabajan de manera coordinada dentro de una red privada y aislada:

\begin{table}[H]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{Servicio} & \textbf{Imagen base} & \textbf{Función} \\
\hline
\texttt{postgres} & PostgreSQL 16 & Base de datos principal \\
\texttt{redis} & Redis 7 Alpine & Broker de mensajería \\
\texttt{backend} & Python 3.12 Slim & API FastAPI + Uvicorn \\
\texttt{worker} & Python 3.12 Slim & Worker Celery \\
\texttt{frontend} & Nginx Alpine & Serve SPA + Proxy inverso \\
\hline
\end{tabular}
\caption{Contenedores Docker utilizados en la infraestructura.}
\end{table}

Un script de instalación (\texttt{start.sh}) automatiza la puesta en marcha completa del sistema: genera las contraseñas y claves de seguridad del entorno de manera aleatoria, construye los contenedores, espera a que la base de datos esté lista, aplica las migraciones pendientes y crea la cuenta del administrador inicial, de modo que el sistema quede operativo con una sola instrucción.

\subsection{Despliegue Automático y Continuo (CI/CD)}

En congruencia con el principio de \textit{flujo continuo} de la metodología Kanban descrito en la Sección \ref{sec:metodologia-kanban}, el paso de una funcionalidad terminada hacia el entorno de producción no se realiza de forma manual. En su lugar, el propio servidor funciona como un ``ejecutor'' (\textit{runner}) de GitHub Actions: cada vez que se integra una nueva versión del código a la rama principal del repositorio, el servidor recibe la notificación de manera automática y ejecuta, sin intervención humana, los siguientes pasos:

\begin{enumerate}
    \item Descarga la versión más reciente del código fuente desde el repositorio.
    \item Reconstruye únicamente los contenedores cuyo código haya cambiado.
    \item Aplica las migraciones de base de datos pendientes.
    \item Reinicia los servicios afectados, restableciendo la disponibilidad del sistema en cuestión de segundos.
\end{enumerate}

Esta automatización reduce considerablemente el margen de error humano durante el despliegue y permite que las mejoras solicitadas por la Dirección Académica estén disponibles para su uso poco después de haber sido validadas, tal como lo señala el tablero Kanban del proyecto.

Para el entorno de desarrollo, el script \texttt{dev.sh} levanta todos los servicios con \textit{hot-reload} activo: los cambios en el código del backend o del frontend se reflejan instantáneamente sin necesidad de reconstruir los contenedores.

\section{Pruebas}
% ============================================================

La estrategia de pruebas del sistema cubre los componentes más críticos de la lógica de negocio mediante pruebas automatizadas ejecutadas con \textbf{pytest}.

\subsection{Pruebas Unitarias}

Se implementaron pruebas unitarias para las funciones de cálculo de fórmulas y los servicios de validación de datos:

\begin{itemize}
    \item \textbf{Fórmulas estadísticas:} Se verificó que la función de cálculo de matrícula actual respete la fórmula oficial $M = T - B_r - B_d + NI$ y que el cálculo de porcentaje maneje correctamente el caso de denominador cero.

    \item \textbf{Procesador CSV:} Se probaron los siguientes escenarios:
    \begin{itemize}
        \item Rechazo de filas con tipos de datos incorrectos (entero esperado, texto recibido).
        \item Rechazo de filas con valores numéricos negativos.
        \item Conversión de valores \texttt{NaN} opcionales a \texttt{None} para compatibilidad con la base de datos.
        \item Normalización de valores a formas canónicas (ej. \texttt{p.a.} → \texttt{P.A.}).
        \item Rechazo de puntajes fuera del rango permitido (1--10 para evaluación docente).
        \item Rechazo de valores infinitos o no numéricos en campos de tipo flotante.
    \end{itemize}
\end{itemize}

\subsection{Pruebas de Validación de Reglas de Negocio}

Se automatizaron pruebas para las validaciones que requieren contexto de la base de datos:

\begin{itemize}
    \item \textbf{Validación de becas tipo ``Madres solteras'':} Se verificó que el sistema rechace registros con sexo masculino para este tipo de beca y que la cantidad de madres solteras no pueda superar el total de mujeres matriculadas en el mismo programa y ciclo.
    \item \textbf{Validación de ciclos en catálogo:} Se verificó que el sistema rechace datos de ciclos escolares que no existan en el catálogo de ciclos generacionales habilitados.
    \item \textbf{Análisis de archivos Excel:} Se probó la detección automática de hojas, encabezados y mapeo de columnas en archivos con estructuras no estándar.
    \item \textbf{Detección de cambios en re-cargas:} Se verificó el módulo de comparación de datos que identifica filas nuevas, modificadas y sin cambios entre una carga previa y la nueva.
\end{itemize}

\subsection{Herramientas de Calidad de Código}

Adicionalmente a las pruebas funcionales, el proyecto aplica las siguientes herramientas de verificación estática configuradas en \texttt{pyproject.toml}:

\begin{itemize}
    \item \textbf{Ruff:} Linter con reglas de estilo, complejidad, buenas prácticas y seguridad.
    \item \textbf{Mypy (modo estricto):} Verificación estática de tipos en todo el código del backend.
    \item \textbf{pytest-cov:} Generación de informes de cobertura de código de las pruebas.
\end{itemize}
