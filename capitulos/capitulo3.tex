\section{Metodología: Kanban}
\label{sec:metodologia-kanban}
% ============================================================

Para el desarrollo de la plataforma se adoptó \textbf{Kanban} como metodología ágil ligera, fundamentada en la gestión visual del flujo de trabajo \cite{anderson2010}. A diferencia de los marcos que estructuran el desarrollo en iteraciones fijas (\textit{sprints}) como Scrum \cite{scrumguide} o eXtreme Programming \cite{beck2004}, Kanban propone un \textbf{flujo continuo} donde las tareas avanzan de forma progresiva por un tablero visual dividido en columnas que representan los estados del proceso. El término proviene del japonés (\textit{señal visual} o \textit{tarjeta}) y fue concebido originalmente por Toyota en la manufactura para ser posteriormente adaptado a la ingeniería de software por David J. Anderson, quien formuló sus principios y prácticas esenciales \cite{anderson2010}.

\subsection{Principios de Kanban Aplicados al Proyecto}

Los cuatro principios fundamentales de Kanban que guiaron el desarrollo de esta plataforma son:

\begin{enumerate}
    \item \textbf{Visualización del flujo de trabajo:} Todas las tareas del proyecto (funcionalidades, correcciones, optimización del esquema de base de datos) se representaron como tarjetas en un tablero, permitiendo al equipo identificar el estado de avance de cada componente en todo momento.

    \item \textbf{Limitación del trabajo en progreso (WIP --- Work In Progress):} En cada etapa del tablero se limitó el número de tareas activas simultáneamente. Esto evitó la sobrecarga del equipo y aseguró que cada módulo fuera completado y validado antes de iniciar el siguiente.

    \item \textbf{Gestión del flujo continuo:} En lugar de planificar iteraciones de duración fija, las tarjetas de trabajo fluyeron de manera continua desde el estado \textit{Pendiente} hasta \textit{Desplegado}, priorizando aquellas funcionalidades con mayor impacto en los usuarios de la Dirección Académica.

    \item \textbf{Mejora continua (Kaizen):} Durante el desarrollo se realizaron reuniones periódicas de revisión en las que se analizaron cuellos de botella, se corrigieron decisiones de diseño previas y se refinaron tanto el esquema de datos como las interfaces de usuario.
\end{enumerate}

\section{Arquitectura del Sistema}
% ============================================================

El sistema adopta una \textbf{arquitectura de tres capas} en su concepción lógica, implementada físicamente mediante contenedores Docker orquestados con Docker Compose. El flujo de tráfico se estructura de la siguiente manera:

\begin{center}
$ \texttt{Nginx (Puerto 80/443)} \longrightarrow \begin{cases} \texttt{React SPA} & \text{(archivos estáticos)} \\ \texttt{FastAPI} & \text{(peticiones /api/*)} \end{cases} \longrightarrow \begin{cases} \texttt{PostgreSQL 16} \\ \texttt{Redis 7} \longleftrightarrow \texttt{Celery Worker} \end{cases} $
\end{center}

\subsection{Capa de Presentación (Frontend)}

Desarrollada en React 18 con TypeScript y compilada por Vite, esta capa implementa una \textbf{Aplicación de una Sola Página (SPA)} que se carga completamente en el primer acceso del navegador. Todas las interacciones posteriores consumen únicamente datos en formato JSON desde la API, sin recargar la página completa. Los tableros estadísticos se renderizan mediante Apache ECharts, y el estado global de los filtros se administra con Zustand.

\subsection{Capa de Lógica de Negocio (Backend)}

El núcleo del sistema está implementado con FastAPI sobre Python 3.12. Esta capa expone 15 routers con endpoints REST, aplica las reglas de validación mediante Pydantic, gestiona la autenticación mediante JWT y coordina el procesamiento asíncrono de archivos a través de Celery. Las interacciones con la base de datos se realizan de forma asíncrona mediante SQLAlchemy 2.0 con el driver \texttt{asyncpg}.

\subsection{Capa de Datos y Mensajería}

\begin{itemize}
    \item \textbf{PostgreSQL 16:} Almacena de forma persistente todos los datos académicos e institucionales, con propiedades ACID garantizadas.
    \item \textbf{Redis 7:} Actúa como broker de mensajería entre FastAPI y los workers de Celery, almacenando temporalmente las tareas de procesamiento pendientes y sus resultados.
    \item \textbf{Celery Worker:} Proceso independiente que ejecuta en segundo plano el análisis, validación y carga masiva de archivos CSV y Excel, sin bloquear el hilo principal de la API.
\end{itemize}

\subsection{Autenticación y Control de Acceso}

El sistema implementa autenticación sin estado mediante JWT. Al iniciar sesión, el servidor genera dos tokens firmados con una clave secreta aleatoria de 32 bytes:

\begin{itemize}
    \item \textbf{Token de Acceso:} Vigencia de 15 minutos. Se incluye en la cabecera \texttt{Authorization: Bearer \textless token\textgreater} de cada petición a la API.
    \item \textbf{Token de Refresco:} Vigencia de 7 días. Se utiliza únicamente para solicitar un nuevo token de acceso sin requerir credenciales nuevamente.
\end{itemize}

El control de acceso basado en roles (RBAC) se implementa mediante dependencias de FastAPI (\texttt{Depends}) que verifican el campo \texttt{role} del token decodificado antes de permitir el acceso a cada endpoint protegido.

\section{Procesamiento de Datos: Pandas y Celery}
% ============================================================

El módulo de carga de archivos es el componente más complejo del sistema. Su diseño responde al requerimiento de procesar archivos de hasta 200 MB sin degradar la experiencia del usuario. El flujo de procesamiento es el siguiente:

\begin{enumerate}
    \item El usuario selecciona y sube un archivo CSV o Excel desde la interfaz web.
    \item FastAPI recibe el archivo, lo almacena temporalmente en el servidor y registra un \texttt{UploadJob} en la base de datos con estado \texttt{pending}.
    \item FastAPI encola una tarea en Celery a través del broker Redis y responde de inmediato al cliente con el identificador único del trabajo (\texttt{job\_id}).
    \item El worker de Celery retoma la tarea de la cola y ejecuta el procesamiento completo:
    \begin{itemize}
        \item Parsea el archivo con Pandas, detectando automáticamente el separador, la codificación y la fila de encabezados.
        \item Valida cada fila: tipo de dato, valores negativos, valores fuera de rango, valores no permitidos según el catálogo y consistencia con la base de datos.
        \item Elimina duplicados internos en el archivo mediante las claves de deduplicación definidas por tipo de dataset.
        \item Ejecuta un \textit{upsert} masivo en PostgreSQL mediante \texttt{INSERT ... ON CONFLICT DO UPDATE}.
    \end{itemize}
    \item El \texttt{UploadJob} se actualiza con el resultado: filas procesadas, filas con error y lista detallada de los primeros 500 errores.
    \item La interfaz del usuario consulta periódicamente el estado del job hasta que el procesamiento concluye.
\end{enumerate}

El sistema define 7 tipos de datasets estructurados con sus correspondientes reglas de validación y restricciones:
\begin{itemize}
    \item \texttt{matricula}: Registro de matrícula general, nuevo ingreso, bajas y desglose por género.
    \item \texttt{evaluacion\_academica}: Calificaciones y promedios por programa educativo.
    \item \texttt{titulacion}: Cohortes generacionales, egresados y titulados.
    \item \texttt{evaluacion\_docente}: Calificaciones a docentes asignadas por estudiantes y directivos.
    \item \texttt{becas}: Distribución de apoyos y becas institucionales.
    \item \texttt{discapacidad}: Caracterización del alumnado con necesidades especiales.
    \item \texttt{etnia}: Registro de pertenencia a pueblos y comunidades originarias.
\end{itemize}

\section{Cálculo de Indicadores Académicos}
% ============================================================

Los indicadores estadísticos calculados por el sistema corresponden a las métricas oficiales de evaluación institucional. Las fórmulas matemáticas implementadas son las siguientes:

\begin{table}[H]
\centering
\begin{tabular}{|l|l|}
\hline
\textbf{Indicador} & \textbf{Fórmula} \\
\hline
Matrícula Actual & $M = T - B_r - B_d + NI$ \\
\hline
Índice de Reprobación & $IR = \dfrac{B_r}{T} \times 100$ \\
\hline
Índice de Deserción & $ID = \dfrac{B_d}{T} \times 100$ \\
\hline
Aprovechamiento & $A = \dfrac{\sum (P_{PE} \times N_{PE})}{\sum N_{PE}}$ \\
\hline
Eficiencia Terminal & $ET = \dfrac{CE}{MG} \times 100$ \\
\hline
Índice de Titulación & $IT = \dfrac{TIT}{CE} \times 100$ \\
\hline
Cobertura & $COB = \dfrac{M}{PEE} \times 100$ \\
\hline
Absorción NMS & $ABS = \dfrac{NI}{E_{NMS}} \times 100$ \\
\hline
\end{tabular}
\caption{Fórmulas matemáticas de los indicadores institucionales.}
\end{table}

Donde: $T$ = total de alumnos, $B_r$ = bajas por reprobación, $B_d$ = bajas por deserción, $NI$ = nuevo ingreso, $P_{PE}$ = promedio del programa educativo, $N_{PE}$ = número de alumnos del PE, $CE$ = concluyeron estudios, $MG$ = matrícula generacional, $TIT$ = titulados, $PEE$ = población en edad escolar, $E_{NMS}$ = egresados de nivel medio superior.

Todos los indicadores soportan filtros dinámicos por subsistema, ciclo escolar, cuatrimestre y programa educativo, calculándose en tiempo real sobre los datos almacenados en PostgreSQL.

\section{Infraestructura y Despliegue}
% ============================================================

El aprovisionamiento de la infraestructura y el diseño de la topología de despliegue se orientaron a garantizar la alta disponibilidad, seguridad y portabilidad de la plataforma. Esta sección detalla la configuración del servidor de producción, los mecanismos de red y la automatización del despliegue continuo (CI/CD).

\subsection{Aprovisionamiento y Seguridad del Servidor Host}

El sistema se aloja en un servidor físico dedicado con sistema operativo Ubuntu Server Linux. Para garantizar la seguridad e integridad del host se implementaron las siguientes directivas:

\begin{itemize}
    \item \textbf{Acceso Remoto Seguro:} Configuración de acceso administrativo mediante el protocolo SSH utilizando autenticación por llaves criptográficas públicas/privadas, deshabilitando el acceso directo de root y contraseñas por texto plano.
    \item \textbf{Aislamiento por Contenedores:} Instalación del motor Docker y Docker Compose para ejecutar todos los servicios en espacios de nombres (\textit{namespaces}) y grupos de control (\textit{cgroups}) aislados (véase la Sección \ref{sec:docker-infra}).
    \item \textbf{Políticas de Cortafuegos (UFW):} Configuración estricta de cortafuegos perimetral (\textit{Uncomplicated Firewall}), cerrando todos los puertos innecesarios y permitiendo únicamente el tráfico sobre los puertos 22 (SSH administrativo), 80 (HTTP) y 443 (HTTPS).
\end{itemize}

\subsection{Resolución de Dominio y Enrutamiento Dinámico (DDNS)}

Dado que el enlace de red institucional disponía de direccionamiento IP público dinámico, se integró un cliente de \textbf{DNS Dinámico (DDNS)} para mantener sincronizado el Nombre de Dominio Completamente Calificado (FQDN \texttt{estadistica.ddns.net}) con la IP pública del servidor en intervalos regulares. Esto garantiza que el personal directivo acceda de forma constante y transparente sin verse afectado por reasignaciones de IP en el enlace de telecomunicaciones.

\subsection{Seguridad en Tránsito y Certificados SSL/TLS (HTTPS)}

Todo el tráfico entre los navegadores de los usuarios y el servidor se transmite cifrado bajo el protocolo HTTPS utilizando algoritmos modernos de TLS 1.3. La plataforma implementa un certificado digital X.509 emitido por la autoridad certificadora \textit{Let's Encrypt}, gestionado mediante la herramienta \texttt{certbot} bajo el protocolo ACME, el cual ejecuta tareas programadas para la renovación automática antes del vencimiento del certificado sin requerir intervención manual.

\subsection{Nginx como Proxy Inverso y Servidor Perimetral}

Nginx se configuró como el punto de entrada único perimetral del sistema, desempeñando tres funciones críticas de arquitectura:

\begin{itemize}
    \item \textbf{Redirección HTTPS Obligatoria:} Redirección automática de todas las solicitudes entrantes en HTTP (puerto 80) hacia su versión cifrada HTTPS (puerto 443).
    \item \textbf{Enrutamiento Inverso de Servicios:} Despacho de tráfico hacia el contenedor del backend FastAPI para rutas bajo el prefijo \texttt{/api/*} y servicio de alto rendimiento con encabezados de compresión Gzip para los archivos estáticos de React SPA.
    \item \textbf{Publicación Controlada de Documentación:} Exposición segura de documentación técnica del proyecto, incluyendo los manuales de usuario y diagramas de arquitectura.
\end{itemize}

\subsection{Virtualización con Contenedores Docker}

Para mitigar la divergencia de configuraciones entre entornos de desarrollo y producción (eliminando el antipatrón de dependencias locales del sistema operativo), la plataforma se empaquetó mediante contenedores de software compatibles con el estándar OCI (\textit{Open Container Initiative}).

\subsection{Integración y Despliegue Continuo (CI/CD)}

En concordancia con el principio de \textit{flujo continuo} de Kanban (Sección \ref{sec:metodologia-kanban}), el despliegue a producción se automatizó mediante un \textit{runner} propio de GitHub Actions configurado en el servidor host:

\begin{enumerate}
    \item Al realizar un \textit{merge} o \textit{push} en la rama principal (\texttt{main}), GitHub Actions notifica automáticamente al servidor.
    \item El runner descarga los últimos cambios del repositorio.
    \item Reconstruye de forma incremental únicamente las imágenes de los contenedores modificados.
    \item Aplica las migraciones de base de datos pendientes con Alembic.
    \item Reinicia los contenedores afectados con tiempo de inactividad mínimo (\textit{zero-downtime deployment}).
\end{enumerate}

Para el entorno de desarrollo local, el script \texttt{dev.sh} habilita el modo \textit{hot-reload} tanto en FastAPI como en Vite, permitiendo reflejar cambios de código instantáneamente.

\section{Pruebas}
% ============================================================

La estrategia de pruebas del sistema cubre los componentes más críticos de la lógica de negocio mediante pruebas automatizadas ejecutadas con \textbf{pytest} \cite{myers2011, pressman2020}.

\subsection{Pruebas Unitarias}

Se implementaron pruebas unitarias para las funciones de cálculo de fórmulas y los servicios de validación de datos:

\begin{itemize}
    \item \textbf{Fórmulas estadísticas:} Se verificó que la función de cálculo de matrícula actual respete la fórmula oficial $M = T - B_r - B_d + NI$ y que el cálculo de porcentajes maneje de forma segura denominadores iguales a cero sin generar excepciones de división por cero.

    \item \textbf{Procesador CSV y Validación de Esquemas:} Se cubrieron los siguientes casos de prueba:
    \begin{itemize}
        \item Rechazo de filas con tipos de datos inválidos (cadenas de texto en campos numéricos).
        \item Rechazo de registros con valores numéricos negativos.
        \item Conversión adecuada de valores nulos (\texttt{NaN}) a \texttt{None} para su persistencia en PostgreSQL.
        \item Normalización de cadenas a formas canónicas institucionales (ej. \texttt{p.a.} $\rightarrow$ \texttt{P.A.}).
        \item Restricción de puntajes de evaluación docente en el rango válido de 1 a 10.
        \item Detección y descarte de valores infinitos (\texttt{Inf}) en campos flotantes.
    \end{itemize}
\end{itemize}

\subsection{Pruebas de Validación de Reglas de Negocio}

Se automatizaron pruebas de integración para validar la coherencia contextual en base de datos:

\begin{itemize}
    \item \textbf{Regla de becas para madres solteras:} Se validó que el sistema rechace registros de becas de maternidad asignados al sexo masculino y que la cantidad de becarias no supere el total de mujeres matriculadas en el periodo correspondiente.
    \item \textbf{Validación contra catálogo de ciclos generacionales:} Verificación de que el sistema rechace datasets con ciclos escolares no registrados previamente en el catálogo institucional.
    \item \textbf{Análisis de hojas de cálculo complejas (Excel):} Pruebas de detección automática de libros multidimensionales, cabeceras desplazadas y mapeo semántico de columnas.
    \item \textbf{Detección de diferencias en recargas (\textit{diff upsert}):} Verificación del clasificador de registros que categoriza filas nuevas, modificadas e idénticas en recargas masivas.
\end{itemize}

\end{itemize}
